One-Way Backup

After each commit, LibrAIry copies newly filed files to a remote you have already configured in rclone, verifies each copy, and stops there. One-way means exactly that: nothing is ever read back, changed, or deleted at either end. It is a safety net against losing this machine, not a sync — edit a file on the remote and LibrAIry will neither notice nor object.

What gets copied

Only files already committed to your library — never the inbox, never quarantine. Sizes are what is there today; the backup grows as you commit more.

Backing up to another machine on your network

"Remote" does not have to mean the cloud. rclone talks to a NAS, a Pi or a spare desktop just as well, which costs nothing per month and is usually far faster than an upload — worth doing even if you also back up off-site, since a copy in the same building is not a copy that survives the building.

  1. On this host, run rclone config pointed at LibrAIry's own config file:
    rclone --config {{ host_appdata_dir }}/rclone/rclone.conf config
  2. Choose n for a new remote and give it a name, e.g. nas.
  3. Pick the protocol your machine already speaks: sftp if it has SSH (most Linux boxes, Synology, UNRAID), smb for a Windows or Samba share, webdav for Nextcloud. SFTP needs nothing installed on the other end.
  4. Give it the LAN address and login — for example host 192.168.1.20, user backup. Those credentials go into rclone's own config file, never into LibrAIry.
  5. Put the remote and the folder in the box above, like nas:/mnt/backup/librairy.

A LAN target is fast enough that the bandwidth limit above is usually unnecessary — leave it empty unless the copy is interfering with something.

Move LibrAIry to different folders

There is no folder browser here, and it is not an omission: a web page cannot open a file picker on the machine running the container. Browsers deliberately hide real paths from pages — that is the same rule that stops any website reading your disk — and LibrAIry can only see the four folders Docker has already handed it. So the paths are typed, and the four boxes below fill themselves from one starting folder.

Everything below is filled in from this, and each box stays editable.

What to do with this

Docker decides which folders a container can see when it starts, and cannot be told about new ones while it runs. So changing these is two steps, and LibrAIry does the first for you:

  1. Copy the four lines below into the file called .env, next to your docker-compose.yml. Replace the existing HOST_*_DIR lines if they are already in there.
  2. Run docker compose up -d in that same folder. It stops the current container, starts a new one pointed at the new folders, and keeps your database — nothing is re-scanned from scratch and nothing is lost.
  3. Come back to this page. The table above will show the new paths.

Nothing is written or moved by this page — it only writes text into the box above. Your files stay exactly where they are until you run that command, and even then Docker only changes what the container can see.

LM Studio

Running on another machine? Type its IP — http:// and :1234 are filled in for you.

  1. In LM Studio, open the Developer tab and start the server.
  2. Turn on Serve on Local Network in the same panel. Without it the server only answers its own machine, and LibrAIry times out.
  3. Load a model, then press Test connection to see it listed here.
